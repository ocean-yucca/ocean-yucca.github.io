Job Workflow

  • Stage names can be arbitrary
  • GitLab run stages in order
  • The job in stage_1 runs first, then the jobs in stage_2 run, and finally the jobs in stage_3 run

default:
  image: alpine:latest

stages:
  - stage_1
  - stage_2
  - stage_3

  stage: stage_1

Script Jobs

# .gitlab-ci.yml
image: alpine:latest # define a default image for jobs

stages: # define stages and order
  - build
  - test
  - deploy
  
job_1:
  stage: build
  tags:
    - saas-linux-small-amd64 # select runner with specific tag to run the job
  script:
    - echo "Hello, $GITLAB_USER_LOGIN!" > output_1.txt # generate output file
  artifacts:
    paths:
      - output_1.txt # define the output file path

job_2:
  stage: test
  tags:
    - gitlab-org-docker
  script:
    - mkdir results # create a output folder
    - echo "Test in job 2" > results/output_2.txt
  artifacts:
    paths:
      - results # define output folder path which is relative to the project directory
    expire_in: 1 day # setup expiration days

job_3:
  stage: test
  script:
    - echo "Test in job 3"
    - sleep 20
  needs:
    - job_1 # implement job_3 when job_1 finish

job_4:
  stage: deploy
  script:
    - echo "Deploy job"
Workflow

  1. You push code to GitLab (e.g., commit to main branch)
  2. GitLab CI/CD
    • Parses .gitlab-ci.yml
    • Triggers a pipeline
    • Assigns a job to a Docker-based runner
  3. Runner pulls the image specified in image: (e.g., python:3.10)
  4. Runner creates a container from that image
  5. Runner injects the project source code into the container's working directory
    • Default is /builds/[username or group_name]/[project_name]
  6. The runner runs the job’s script: commands inside the container in working directory
CI/CD Pipeline Engine
  • Parsing .gitlab-ci.yml when you push a commit
  • Building the pipeline graph: which jobs to run, what stages and dependencies exist
  • Scheduling jobs in the correct order
  • Assigning jobs to available runners based on tags, availability, and rules
  • The .gitlab-ci.yml file itself is not "executed" on your runner
Runner
  • What a runner is?
    • GitLab Runner is the program that actually executes the jobs
    • Runner is on a sever which execute jobs
    • Each job run its own container
    • Server can be company server, cloud VM, K8s cluster, personal computer or GitLab-hosted runner
  • Executor modes
    • shell
      • Runs jobs directly in the local shell
      • Jobs can share files
    • docker
      • Default executor of shared runners on GitLab.com
      • Launches a container for each job
      • Each job runs in its own isolated Docker container for security, reproducibility, and separation of concerns
      • Nothing is shared between job containers by default
    • virtualbox
    • ssh
    • kubernetes
  • Tags
    • Tag on a runner, this runner is available for jobs that require these capabilities
    • Tag on a job, this job requires a runner with these tags/capabilities
    • Settings -> CI/CD -> Runners
    • When a job has multiple tags, GitLab looks for a runner that matches all of those tags
Share Files between Jobs
  • artifacts, share files between jobs in a single pipeline

default:
  image: alpine:latest

stages:
  - stage_build
  - stage_test

job_create_file:
  stage: stage_build
  script:
    - echo "Hello from create_file job" > output.txt
  artifacts:
    paths:
      - output.txt

job_use_file:
  stage: stage_test
  dependencies:
    - job_create_file
  script:
    - cat output.txt > output2.txt
  artifacts:
    paths:
      - output2.txt
  • cache, Share files between jobs in the same pipeline

stages:
  - build
  - test
 
create_file:
  stage: build
  script:
    - mkdir -p shared
    - echo "Hello to a cache!" > shared/message.txt
  cache:
    key: shared-cache
    paths:
      - shared
    policy: push
 
use_file:
  stage: test
  cache:
    key: shared-cache
    paths:
      - shared
    policy: pull
  script:
    - echo "Job in the same pipeline reads file from cache:"
    - cat shared/message.txt
  • cache, share files across pipelines

stages:
  - restore

restore_cached_file:
  stage: restore
  cache:
    key: shared-cache
    paths:
      - shared
    policy: pull
  script:
    - echo "Checking cache from previous pipeline..."
    - |
      if [ -f shared/message.txt ]; then
        echo "Found cached file:"
        cat shared/message.txt
      else
        echo "No cached file found. This may be the first pipeline."
      fi
